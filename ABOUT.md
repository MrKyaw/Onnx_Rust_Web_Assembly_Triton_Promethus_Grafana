# About — ONNX Rust WASM Triton Gateway

**Tagline:** The same ONNX model, two delivery paths — compiled to WebAssembly for the browser, served through Triton for the datacenter — wrapped in validation, batching, and observability.

## What the project demonstrates

1. **Client-side ML:** Rust + `tract-onnx` compiled to `wasm32-unknown-unknown`, packaged with `wasm-pack`, usable from a web page without sending data to a server.
2. **Server-side ML:** a Triton v2 HTTP gateway that validates inputs, batches by the first dimension, and maps failures to correct status codes.
3. **Observability:** Prometheus counters and histograms generated by the gateway, scraped alongside Triton metrics and visualized in Grafana.
4. **Operational rigor:** liveness vs readiness, model metadata, configuration from environment, container orchestration.
5. **Test discipline:** 100% line and branch coverage of the gateway core, plus Rust unit tests and a successful WASM release build.

## Architecture in one sentence

`Browser → WASM/tract` and `Client → FastAPI → triton_gateway → Triton v2`, with Prometheus scraping both the gateway and Triton.

## What is verified

- 83 Python tests pass; 77 core tests cover every branch of `triton_gateway`.
- 4 Rust tests pass (`cargo test`).
- `wasm-pack build --target web --release` succeeds.
- FastAPI contract tests cover health, readiness, prediction, validation, and metrics.
- Prometheus exposition includes counters, histograms, bucket boundaries, `+Inf`, `_sum`, and `_count`.

## Honest limitations

- `tract` supports a subset of ONNX; not every model will run in WASM.
- The built-in demo backend returns a deterministic softmax, not a trained prediction.
- The full Docker stack pulls NVIDIA Triton and is heavy; the gateway core runs anywhere.
- Browser-side inference performance depends on model size and device.
